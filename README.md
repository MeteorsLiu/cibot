# cibot

Automation for LLAR Hub, with streaming toc file handling and a GitHub webhook service.

Build the command with `go build -o ci ./cmd/ci`, then run `./ci serve`. The command loads `.env` from its working directory, constructs the bot (which starts its queue worker), and serves GitHub webhooks. Existing process environment variables take precedence over `.env` values. On SIGINT or SIGTERM, the HTTP server stops accepting connections and waits for active requests to finish. Accepted jobs belong to Redis rather than the HTTP request; unfinished jobs are recovered by Asynq after the worker process restarts.

Use `.env.example` as a configuration template:

| Setting | Value |
| --- | --- |
| `WEBHOOK_SECRET` | The secret configured on the GitHub App's webhook. |
| `APP_ID` | The GitHub App's numeric ID. |
| `PRIVATE_KEY_FILE` | Path to the App's PEM private key; relative paths are resolved from the working directory. |
| `LISTEN_ADDR` | HTTP listen address; defaults to `:80` when empty or unset. |
| `REDIS_ADDR` | Redis address reachable by the bot, for example `127.0.0.1:6379` for a local process. |

`internal/bot.Bot` implements `http.Handler`. Construct it with `bot.New(webhookSecret, appID, privateKeyFile, redisAddr)` and attach it to an HTTP server owned by the caller. The webhook secret is a nonempty string. The constructor loads the App's PEM private key, initializes an empty installation-client map, and starts a private Asynq worker. Asynq's client and server stay inside `internal/bot`; there is no public worker-start method. The worker lives for the process lifetime. The secret and authentication configuration must remain unchanged while serving.

The handler verifies POST deliveries using go-github before parsing events and acknowledges webhook pings immediately. Merged PRs targeting `main` in `llarhub/.index` or `MeteorsLiu/llarhub`, and non-deletion pushes to `c`, are placed in the private `cibot` queue. It returns `202` only after enqueue succeeds, or when that task ID already exists. IDs are `<event-type>:<owner>/<repo>@<commit-sha>`: merged PRs use the merge commit SHA, and pushes use `after`. Duplicate deliveries cannot enqueue a second task while its record exists. Successful tasks are removed by Asynq, so this is not permanent deduplication after completion.

Each execution has an explicit 80-hour timeout and uses Asynq's task context, independent of the HTTP connection. Worker concurrency, retries, and lease recovery use Asynq's defaults. Processing errors are returned to Asynq, not to the already-acknowledged webhook request. Ordinary errors retry; the stale/conflicting push and closed toc PR cases below use `asynq.SkipRetry` to archive the task without automatic retries. Redis must remain available. The container includes Redis with AOF persistence; retain its data volume when replacing the container.

The worker lazily creates and caches a GitHub client keyed by the event's installation ID. A mutex protects lookup and creation, but is released before any network requests. Each cached client owns an installation transport that obtains, caches, and refreshes its token through `ghinstallation`. App transport copies isolate the fields changed during token refresh while sharing the parsed key and underlying connections. Clients remain cached for the lifetime of the bot.

Using the installation client, the worker paginates the PR's changed files and deduplicates affected top-level project directories, including both paths of renamed files. Hidden directories and root-level files are ignored. It checks the merge commit's root tree to exclude deleted directories, symlinks, and submodules, then queries each project's repository under the registry's own owner. Test registry events therefore provision `MeteorsLiu/proj`, not `llarhub/proj`.

For each merged-PR task, the worker partially clones the registry with `--filter=blob:none --no-checkout` into a temporary directory. It selects the affected project directories with cone-mode sparse checkout before checking out the merge commit, so only those directories and root-level files are materialized and their contents downloaded. Commit and tree history is retained; this is not a shallow clone. It copies each affected project's configuration into its own working directory and reads the source ID from `versions.json.path`. It updates the aggregate toc PR, then directly loops over the projects to create repositories, generate bindings, and publish branches and tags. A generation failure leaves the toc PR already submitted by the first step intact. Temporary checkouts are removed when that task attempt finishes.

`updateTOC` finds an open PR into `main` whose head belongs to the same registry and uses the `llarhub-bot/toc-pr-` branch prefix. If one exists, the new request appends to that branch's current toc and commits on its current head, preserving earlier pending records. Otherwise it starts a new `llarhub-bot/toc-pr-<first-registration-pr-number>` branch from the latest `main` and opens a PR. Subsequent requests accumulate in that open PR rather than creating separate PRs. A mutex serializes the lookup and update within the bot, so concurrent requests do not create separate aggregation PRs or overwrite each other's additions. Once a PR is closed or merged, the next registration starts a new aggregation cycle.

After updating or reusing an existing toc PR branch, the bot reads that PR's current state once. If it was merged during the update, the task returns a retryable error; the next attempt starts from the latest `main` and adds only mappings still missing there. If all mappings already merged, no new PR is created. A PR closed without merging stops automatic retries for that task and is left for manual review. State lookup errors remain retryable. This also checks the no-new-records path, but does not add a separate merged-PR reconciliation handler or make the Git push and PR state check atomic.

`toc.File.Add` returns `(bool, error)`: a successful append returns true, while finding the literal `full + " " + proj` byte sequence returns false. It uses `bytes.Contains` with a local 64 KiB array and overlapping reads, without parsing existing records, checking field/line boundaries, or rejecting another project mapped to the same source. Each `File` owns a mutex covering the entire lookup and append, so concurrent calls on that instance do not append the same mapping twice. A `File` must not be copied after first use; separate instances targeting the same path still require caller synchronization. A request containing only matching mappings leaves the toc PR unchanged. Once project inputs have been copied out, the bot narrows sparse checkout to root-level files, then fetches and checks out the latest aggregation branch while holding the bot's toc lock. This avoids downloading newer project contents just to update the toc. It appends records and commits and pushes only `llarhub.toc`; unselected directories remain in the commit. File contents stay on disk; the bot does not build an in-memory blob or base64 JSON request. It does not edit the contributor's PR or merge its own toc PR.

`provision` attempts to create an initialized public repository when the project repository lookup returned 404, using the personal-account or organization endpoint; GitHub remains responsible for rejecting inaccessible or occupied names. It copies `llcppg.cfg` unchanged, preserving the authored `LLGoPackage`, `CFlags`, and other configuration fields. For example, libdeflate can use `"LLGoPackage": "link: $(pkg-config --libs libdeflate)"`; libraries with their own configuration tool can use expressions such as `"link: -L$(llvm-config --libdir) -lclang"`. LLGo evaluates these expressions when building the generated package, so consumers must install the matching native library and expose its configuration tool and metadata in their build environment. `CFlags` supplies wrapper compilation flags, not llcppg's header-preprocessing flags. The bot still runs `llar install <source-id> -o <native-dir>` using `versions.json.path` to obtain headers, copies them into the source configuration directory, and invokes the generator as `llcppg <output-dir> <source-dir>`. It prepares the generated package's `go.mod` with `go mod edit -module github.com/<owner>/<proj>` and `go mod tidy`.

The submitted project directory contains `versions.json`, the LLAR formula, and `llcppg.cfg`. Publication copies only `llcppg.cfg`, `include/`, `go.mod`, and `go.sum` from the prepared source directory into `c/`; `include/` is copied recursively after overlaying the installed headers. The index does not need `go.mod` or `go.sum`: when not supplied, the bot retains the template's or existing C branch's module files, or initializes them when creating a missing C branch. Formula version directories, `versions.json`, and other index files are not copied into `c/`. Files already in an existing C branch are left in place unless overwritten by one of the four selected entries; this does not clean up previously published formulas. Prefix trimming and other binding choices remain human-authored. The runtime must have Git with `--config-env` support, `llar`, an `llcppg` with `-init` support built with LLGo, and the required Go/LLVM environment on `PATH`.

Project publication uses a local clone. For a newly created repository, `llcppg -init <proj>` commits the template's `c` and `main` branches before the bot overlays the registered configuration and headers under `c/`. A private mutex serializes only `-init` calls within the bot because llcppg shares a template cache; generation and publishing remain outside that lock. The bot changes the C module path to `github.com/<owner>/<proj>/c`, including for personal-account test repositories.

An existing `c` branch retains its history and module dependencies. When an existing repository has no `c` branch, the bot starts it from the default branch and initializes its C module with Go 1.23 and `github.com/goplus/lib v0.6.1`. Generation uses that branch's `c/` directory, and generated bindings are committed to the repository's default branch. Files are overlaid without removing unrelated repository files. Branches are pushed with explicit refspecs and without force. When both initial tags are absent, publication creates `c/v0.1.0` for the source module and `v0.1.0` for the generated module, including when an earlier attempt created the repository but failed before publication. If either initial tag exists, neither is created or moved. Initialization or generation failure does not publish project branches or tags.

GitHub API calls handle repository discovery/creation and PR operations. Git handles checkout, file transfer, commits, branches, and tags. Each Git process obtains its installation's cached/refreshed token and receives it through an environment-backed HTTPS authorization header scoped to `github.com`. Credentials are not placed in command arguments, clone URLs, or persistent Git configuration. Commits use the `llarhub-bot[bot]` identity; Git identity and credential settings apply only to that process. The `llcppg -init` child process receives Git author and committer identity through its own environment, without the installation token.

For non-deletion pushes to `c`, the worker first checks registration in the corresponding index: `llarhub/<project>` requires `<project>/versions.json` on `llarhub/.index:main`, and `MeteorsLiu/<project>` requires that file on `MeteorsLiu/llarhub:main`. Other owners, missing registrations (HTTP 404), and metadata paths that are not files are ignored without cloning or generating. Other lookup errors are returned to Asynq for retry. The installation must have access to both the project repository and its index. This check runs in the worker on every attempt, so the webhook still acknowledges enqueueing without waiting for GitHub, and removing a registration prevents later attempts from generating. The pending toc PR is not consulted: the project registration is already merged before the bot's initial c-branch push.

For a registered project, the worker clones the repository and compares the cloned `c` HEAD with the event's `after` SHA. A mismatch archives that task without invoking the generator. For example, if `c` has advanced to C, queued tasks for A and B both stop. Matching tasks check out `after` and use its `c/` directory as the generation input. That directory supplies `go.mod`, `llcppg.cfg`, and headers; a local `versions.json` and another `llar install` are not needed for this path. It uses the same generation and module preparation code as registration, then commits the output to the repository's default branch. The commit message identifies the source SHA. The source branch and existing tags are left unchanged, and ordinary pushes do not create version tags or toc PRs.

Immediately before publishing, the worker reads the remote `c` and default-branch HEADs again. If either differs from the clone's starting SHA, it discards the generated output and archives the task without retrying. If another writer advances the target between that check and the push, the ordinary non-forced push rejects the update; a follow-up HEAD check classifies the conflict as non-retryable. Unrelated command, API, or push failures retain their normal retries. These are checkpoint checks, not real-time interruption of a running llcppg process, and the ref check and push are not atomic. The bot does not force-push, rebase, or pause the repository; future `c` pushes are processed normally.

Registration and c-branch generation run asynchronously after enqueue. Enqueue failures return 500, invalid signatures are rejected with 403, invalid event payloads with 400, and unrelated events are acknowledged with 204. GitHub delivery retries and Asynq job retries are separate: an event that never reached Redis still needs redelivery from GitHub.

The integration tests use isolated miniredis instances with the actual Asynq client and worker, simulate the GitHub API, and substitute the `llar` and `llcppg` executables, while running real Git commands against temporary local bare repositories. They verify early webhook acknowledgment, independence from request cancellation, task IDs and timeouts, enqueue failures, published files, retained commit history and tags, toc PR aggregation under concurrent deliveries, installation authentication, and rejection of non-fast-forward pushes. They do not replace a real-toolchain generation test or a live GitHub deployment check.

Local deployment settings belong in `.env`, which is ignored by Git. Keep the private key outside the repository.

## Container

The image includes `ci`, Redis, Git, Go, LLAR, llcppg, and the LLVM 22/LLGo toolchain used to build the generator. Tool source revisions are pinned in the Dockerfile. Published images target Linux amd64. The internal entrypoint starts Redis, waits for `PING` to return `PONG`, then starts `ci serve`. Redis listens on `127.0.0.1:6379`, matching the default `REDIS_ADDR`, and is not published outside the container. HTTP still listens on port 80.

Redis stores its AOF data in `/var/lib/redis`, using its default every-second fsync policy. Use a named volume to keep queued jobs across container replacement. The entrypoint forwards termination to the bot first and then stops Redis so it can flush its data; if either service exits, the other is stopped and the container exits.

```sh
docker build --platform linux/amd64 -t cibot:local .
docker run --rm --platform linux/amd64 -p 80:80 --env-file .env \
  --mount type=volume,src=cibot-redis,dst=/var/lib/redis \
  --mount type=bind,src=/absolute/path/to/app.private-key.pem,dst=/run/secrets/github-app.pem,readonly \
  -e PRIVATE_KEY_FILE=/run/secrets/github-app.pem \
  cibot:local
```

The image contains only the public `.env.example` defaults. Real `.env` files, private keys, and Git metadata are excluded from the build context. Use a container-visible private key path as shown above, rather than the host path stored in your local `.env`. Keep `REDIS_ADDR=127.0.0.1:6379` when using the bundled Redis. Do not remove the Redis volume when upgrading if its queued jobs must be retained.

## GitHub Actions

- `Go` runs on pull requests and pushes to `main` or tags. It runs vet and race-enabled tests, generates `coverage.out`, and uploads coverage to Codecov. Set the repository Actions secret `CODECOV_TOKEN` to its Codecov upload token. Upload failures fail this workflow; public fork PRs use Codecov's supported tokenless upload path when the secret is unavailable.
- `Docker` runs on pull requests and tag pushes. PRs build the Linux amd64 image without logging in or pushing. Tag pushes publish `ghcr.io/meteorsliu/cibot:<git-tag>` using `GITHUB_TOKEN` with `packages: write`. Image names are lowercased and tag characters are normalized by Docker's metadata action. No additional `latest` tag is published.

Both workflows use `ubuntu-latest`. GHCR publishing does not require a separate registry password.
